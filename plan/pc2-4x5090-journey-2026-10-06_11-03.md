## 阶段一：方案规划（10-06）

### 起点

我给了一份 v3.6 计划，目标是在 4×5090 上跑 QWEN-PEDIA r10。r10 是 QWEN-PEDIA 项目里 Qwen3.8-Flash-Next 部署配方的**第 10 个修订版**，不是模型名。它的内容是 NVFP4 权重 + vLLM 补丁（overlay，其中有让 PCIe 卡也能用 custom all-reduce 的开关）+ TP4/EP 启动参数。作者给的基线：decode 319–331 tok/s，prefill 约 7,800 tok/s，主机内存约 125GB（其中 48GB 的 PLE 表要锁在内存里）。

### 遇到的问题和我的处理

**1. 选哪台机器当推理服务器**

| 版本 | 推荐 | 原因 |
|---|---|---|
| v3.7 | 备用 Intel 主板 + 12700K + 4×32GB DDR4 | X870E 当时只有 96GB，不够 125GB |
| v3.8 | X870E 插满 4×48GB DDR5（192GB） | 我说有 4 根 48GB，其中两根还没插；128GB 只剩约 3GB 余量 |
| v3.9 | 回到 Intel 主板跑纯 Ubuntu，X870E 继续当 Win10 日常机 | 我的倾向：主力机不装双系统 |

这里有一个当时没发现的错误：我一直把主板写成 **Z790-A D4**，直到 10-28 你拿出手册才发现是 **Z690-A D4**（见阶段四）。

v3.7 时我还查出原计划的几个错误：BAR1 抄成了 5060 Ti 的 16GiB（5090 要 32GiB）；`setpci` 关 ACS 重启会丢；预算前后不一致；官方 vLLM 在 PCIe、超过 2 卡时会关掉 custom all-reduce，所以验收必须用 r10 的补丁版和固定的 vLLM 版本。

**2. 电源能不能混用**

你担心“频率不齐，有的卡不启动”。我查证后的结论：

- **频率不齐不会发生**：PCIe 参考时钟来自 switch 或主机，与 12V 来自哪台电源无关。
- **真正要防两件事**：一是从电源上电晚了，卡错过 PERST# 握手而不识别；二是**同一张卡的插槽供电和 12V-2x6 来自两台电源**，压差或单台掉电会让电流倒灌。Level1Techs 有人因此烧了两张 3090。
- **原则定为“同卡同源”**：一张卡的所有供电来自同一台电源；所有电源同步上电；运行中不单独关任何一台。

**3. 一体背板做不到同卡同源**

你指出：背板的槽供电是背板统一提供的，严格同卡同源就得让背板加 4 张卡全用一台电源，而 115V 下单台 ATX 电源最大 1600W，带不动。我搜索后确认：

- ADT-Link 5 槽背板槽距只有 40.6mm，3 槽的 5090 插不下。
- c-payne 的 switch 板页面写明“Intel Mainstream as of now is not compatible”。
- **改用分体 kit**：switch 卡插在主板上，每张 GPU 接一块自带 12V 输入的转接板，天然满足同卡同源，间距也不受限。

当时还发现一个新风险：能找到的 88096 成功案例都在 AM5、EPYC、Threadripper 上，**没有 Intel 消费级平台的**。所以我把“识别不到 switch 就整套搬到 X870E”写成了回退方案。

**4. 引用核对**

我给了 4 条 Reddit 帖子的摘要，要求文内引用并逐帖核对。内置浏览器、抓取、搜索都打不开 Reddit，我把原文贴给了我。核对结果：3 条准确，r/homelab 那条“molex 不够、无论如何要加电源”语气说重了，原文是“might need”，我改成了原话的语气。

**结果**：完整版 v3.9 定稿，推荐方案是 Intel 主板 + 纯 Ubuntu + 分体 PEX88096 + 多电源同卡同源。

## 阶段三：计划修订 v1.1–v1.6（10-20 到 10-25）

### v1.1 → v1.2：检查出 4 处会导致误判的问题

| 问题 | 后果 | 改法 |
|---|---|---|
| G1 空载检查 LnkSta | 5090 空闲降到 2.5GT/s，会被误判为链路故障 | 速率在负载下看；宽度空载也不应降 |
| 缺 `NVreg_EnableResizableBar=1` | BAR1 可能停在 256MB，P2P 不通 | 写进 modprobe |
| 装机前测 r10 内存峰值 | 没有 4 张卡就跑不了 TP4 | 改成模拟测试，真实测试挪到 G3 之后 |
| 写成“转接板 DIP” | DIP 在 switch 卡上 | 改正 |

另外改用 apt 优先级规则禁止安装发行版 nvidia 驱动（`apt-mark hold nvidia` 会报错）。卖家答复“线通用、两头相同、白色 4-pin 是风扇口”后，也写进了 v1.2。

### v1.3：240V 供电

我住的是临时住所，不改固定线路、不拆配电箱和墙插。现有条件是一个 NEMA 10-30R 干衣机插座（双极 30A 断路器）。方案定为：

```text
配电箱 30A 双极 → NEMA 10-30R → 成品 10-30P→L6-30R adapter → L6-30P 输入的 240V PDU → 3 台 PSU
```

- 30A 回路持续上限 24A。每卡 400W 时约 8.8A，余量很大。
- **风险写明**：这个 adapter 借用 10-30 的中性线当保护地，你接受这个风险。我写了不改线也能做的缓解措施，以及首次上电流程：负载下电压比空载低超过约 2%（约 5V）就查接触；接头比环境高 10°C 要查，高 20°C 立即停机。

### 无审查模型

我问能不能用 uncensored 模型。我查了两个版本：

| 版本 | 问题 |
|---|---|
| OrcaRouter Uncensored（GGUF / NVFP4） | GGUF 只能用 llama.cpp 按层切卡，速度低；NVFP4 版的 PLE 表是 BF16，约 100–130GB，128GB 内存基本不够 |
| mazinb Uncensored NVFP4 | 拼接版本，只在单卡 DGX Spark 上测过，PLE 运行时约 95GB，量化没有校准 |

**结果**：我决定“先用官方 r10”。

### v1.4 → v1.6：按实物核对电源

你核实了全部电源，并说明库存一共有 **13 张 5090**，用显卡自带的英伟达 4×8-pin 转接线；PC1 保持现状，不接 240V。

| 遇到的问题 | 处理 |

你描述了三种布局。我先纠正了一个前提：**显卡风扇那一面是进风，不是出风**。我说明我把风扇面叫“下面”。按 3 槽三风扇非公版卡来看：

## 阶段四：装系统和单卡验收（10-28 到 10-29）

### 内存和主板型号

- 128GB 全部识别，按 JEDEC **DDR4-2666 CL19** 运行，MemTest86+ 0 错误。我当时决定 XMP 保持关闭。
- 我给了手册，我发现是 **Z690-A**，不是 Z790-A。我要求“立刻改正计划”，写成 **v1.7**。按手册：
  - switch 卡**只能插 PCIEX16(G5)**（CPU 直连 Gen5 x16）；第二个 x16 长槽来自芯片组，只有 PCIe 3.0 x4。
  - M.2_1 是 CPU 单独的 Gen4 x4，手册没写和 x16 共享。所以你保留系统盘在 M.2_1，我取消了“先空槽对比”的测试，改为直接看 switch 上行是不是 x16。

### 装 Ubuntu

- 我给了 Rufus 制作 U 盘（GPT + UEFI non-CSM，校验 SHA256）和安装每一屏的步骤。
- **不勾选 “Search for third-party drivers”**：我问为什么不能事后覆盖。原因是发行版驱动用 DKMS 装在 `updates/` 目录，优先级更高，内核升级时会悄悄换掉补丁模块，P2P 失效却不报错；用户态库版本也会对不上。
- 结果：IP 192.168.1.OBFUSCATED，内核 **6.8.0-147-generic**（GA 分支）。

### SSH 和驱动

- `ssh-keygen` 提示覆盖时，我让你输入 **n**，用已有的密钥，避免影响 GitHub 等其他地方。
- 发现 BIOS 开着 Intel VMD，NVMe 挂在 `10000:` 域下。我决定先不管。ufw 你也决定先关着。
- 驱动安装：用户态用 runfile 加 `--no-kernel-modules`；内核模块用 aikitoria 补丁版 `make modules_install`。第一次多行粘贴被终端搅乱，`depmod` 没执行，我改为每次只粘贴一行。
- 屏蔽 nouveau、加 `NVreg_EnableResizableBar=1`、内核参数 `intel_iommu=on iommu=pt pcie_aspm=off`，都打进 initramfs。

### 接上 switch 后断网

| 现象 | 原因 | 处理 |
|---|---|---|
| 重启后网口不亮灯、连不上 | switch 卡占掉一大段 PCI 总线号，网卡从 `enp4s0` 变成 `enp22s0`，netplan 写死了旧名字 | 先用 `sed` 改名恢复，再把 netplan 改成**按 MAC 匹配**，以后插拔设备不会再断网 |

### 单卡验收

| 问题 | 原因 | 处理 | 结果 |
|---|---|---|---|
| 驱动拒绝加载，BAR0 为 0 | 5090 带 SR-IOV 虚拟功能；Ubuntu 内核开着自动重分配，释放了 BIOS 已分配的窗口 | 启动参数 profile 2：`pci=disable_acs_redir=pci:1000:c010,realloc=off`（你第一次没执行 sed，第二次才生效） | BAR1 32GiB，驱动加载 |
| GPU 链路只有 x8 | 线序反了 | 在转接板端对调两根线 | x16 |

**定下来的线序：编号 1 的口（A1/B1/C1/D1）→ 转接板 ②，编号 2 的口 → 转接板 ①，不能跨字母。**

单卡结果：switch ID `1000:c010`；上行 Gen4 x16；BAR1 32768 MiB；ACS 在 14 个下行口都是 0x0000；AER 0；H2D 23.7 GB/s，D2H 28.4 GB/s。

### 授权和功率

- 我问怎么授权 sudo。我**不要密码**，改为在服务器上建 `/etc/sudoers.d/90-USER-nopasswd`，并约定用完收回。
- 我决定直接接 4 张卡，并告知 240V PDU 已在用。
- 我建议满载前给 GPU0/GPU1 设 500W、GPU3 设 400W，因为不限时 High Power 持续负载约 92%，Super Flower 约 85%，而它是主控，一保护就整机断电。**我决定都不限**。我把风险写进文档，并约定用分阶段满载测试来验证。

## 阶段五：4 卡跑通（10-29 到 10-30）

这是整个项目最难的一关，对应计划里排第二的风险：BIOS 的 MMIO 窗口。

### 排查过程

| 步骤 | 现象 | 我的判断 |
|---|---|---|

### 根因

我读 `/proc/iomem` 后发现：BIOS 给 64 位 PCIe 设备只留了 **256GB**（0x40_0000_0000–0x7F_FFFF_FFFF），而核显（含 SR-IOV 虚拟功能）占了开头那段。每张 5090 有 32G 的 BAR1 和 32M 的 BAR3，按 32G 对齐后实际要占掉约 64G。2 张放得下，3 张就分配失败，POST 卡在 VGA。

我给了两篇文章：

- **文章 1**（linux-pci 邮件列表，Britton）：Linux 7.0 起的回归（提交 3958bf16e2fe），父桥窗口算小，32G + 32M 结构的卡分不到 BAR。6.8–6.19 没有这个问题。
- **文章 2**（Matt Protacio，ASUS Z790-P + PEX88096 `1000:c010` + 4 张 32G BAR 的卡）：和我几乎一样，BIOS 卡 POST。他的 V100 根本没有 ReBAR，照样卡，所以关核显多半救不了。他的办法是绕开 BIOS，让 Linux 来分配。

### 解决方案

1. **BIOS Re-Size BAR = Disabled**（Above 4G 保持开）：BIOS 只分 256MB 的小 BAR，POST 能过。
2. **内核参数加 `pci=nocrs`**：ReBAR 关掉后芯片组设备落在 0x6074…，窗口被切碎，remove/rescan 报“no space”；加了之后根总线能用完整的 46 位地址空间。
3. **开机服务 `gpu-rebar.service`**：在加载驱动之前，用 `setpci` 把每张卡的 ReBAR 控制寄存器（0x13C）改成 32GB，移除并重新扫描根端口 `0000:00:01.0`，再加载 nvidia。
4. **`/etc/modprobe.d/nvidia-defer.conf`**：禁止 nvidia 自动加载，由上面的服务负责。
5. **版本冻结**：永远不要升级到 7.x 内核（7.0–7.3 都有这个回归）。

第一次 ReBAR 关闭后开机，我选了默认启动项，驱动自己调整 BAR 失败（“48G can't assign”）。我卸载驱动后手动走一遍流程，再做成服务。远程重启验证：`gpu-rebar: 4/4 GPUs have a 32G BAR1`。

### 结果

| 项目 | 结果 |
|---|---|
| 4 卡 BAR1 | 全部 32G |
| 链路 | 全部 Gen4 x16 |
| 拓扑 | 卡内两级 switch；`topo -m` 中 bus 08 和 09 同一下级 switch 显示 PIX，其余 PXB；带宽不受影响 |
| P2P（拷贝引擎） | **单向每对 28.57 GB/s（合计 342.9），双向 56.5 GB/s（合计 677.7）** |
| 错误 | Xid、AER、DMAR 均为 0 |

`nvidia-smi` 编号和总线的对应：0=05、1=08、2=09、3=0C。它不一定等于按电源命名的 GPU0–GPU3。

**写成 v1.8**：4 卡 BAR 方案、启动 profile 3、线序、§4.1 实测记录、功率默认不设、不升级 7.x 内核。

### 我问的概念

| 测试 | 结果 |
|---|---|
| 锁核心频率 1200–2400 MHz | 每步耗时符合 `T ≈ 19.5 / f(GHz) + 1.8 ms`，所以单流约 **78% 受核心频率限制** |

| PCIe | 每卡每方向平均只用约 1.3 GB/s，链路速度没直接测 |

## 阶段十一：温度（11-01）

### “为什么高温度反而接受率更高？”

**其实没有，是我之前看错了。** 测试顺序是每个 prompt 先跑温度 0、再跑温度 1，温度 0 总是承担第一次运行的慢速（第一次每步 8–9 ms，之后约 6 ms；专家命中率从 97.5% 升到 99.7%）。去掉第一次后：

| 任务（Basalt，短 prompt + 思考） | 温度 0 | 温度 1 |
|---|---|---|
| 代码 | 392 tok/s（2.45 token/步） | 386（2.28） |
| 文章 | 387（2.22） | 351（1.92） |
| 中文 | 388（2.60） | 328（1.97） |
| 复制文本 | 466（3.87） | 375（2.55） |

两个引擎都是温度越低越快：草稿通常是最可能的词，温度 0 必选它，所以容易命中。

温度 0 + 思考下 r10 → Basalt：代码 292 → 392（+34%），文章 256 → 387（+51%），中文 265 → 388（+46%），复制 329 → 466（+42%）。48 万 token 去掉第一次后：代码 287 → 296（+3%），文章 277 → 248（-10%）。r10 的数字保留了第一次，所以对比略偏向 Basalt，只能看大致差距。11–33 万 token 没测过温度 0。

### 我的偏好

> 我其实更喜欢低温度。我的工作大多数都是倾向低温度，我不需要创意写作或天马行空。

用途是写代码、agent 工具调用、务实回答。我记下了这个偏好，以后对比和配置以低温度为准。

### “模型卡为什么推荐 1.0？温度 0 是不是更好？”

- 模型卡只给参数，没解释原因。思考模式 1.0 / top_p 0.95 / top_k 20；非思考 0.7 / 0.8 / presence 1.5。官方代码榜单就是按 1.0 测的。
- 模型卡提到用 `presence_penalty` 减轻“无尽重复”。论文 [Why Do Reasoning Models Loop?](https://arxiv.org/abs/2512.12895) 说推理模型在低温度下都会循环，温度 0 最严重，厂商推荐高温度是权宜之计。这篇没测这个模型，只是旁证。
- 我自己的疑点：r10 温度 0 回忆测试有 3 次失败，都是 4000–6000 token 全用在思考上、答案为空，和循环症状相符，但没保存文本，无法确认。
- 也更正了 Basalt 回忆 8/8 的意义：它有思考预算，到上限强制收尾（日志里有一次在 4500 token 处收尾），r10 没有这个机制。

**我不建议默认严格的温度 0**，选择规则也从“先看速度”改为“先看可靠性”：用约 20 个代码和 agent 任务、开思考，比较 0 / 0.3 / 0.6 / 1.0，记录循环率（同一个 30-gram 出现至少 20 次）、无答案率、正确率和 tok/s，选循环率和无答案率都不比 1.0 差的最低温度。

### “QwenCloud 云端默认是 0.6，为什么？”

[QwenCloud 文档](https://docs.qwencloud.com/developer-guides/getting-started/latest-model)写的是：

> "In thinking mode, `temperature` defaults to 0.6; smaller values are automatically adjusted to 0.6."

- **0.6 不只是默认值，还是开思考时的下限**，传 0 也会被改成 0.6。关思考时没有这个限制。我上一条只说“默认 0.6”，漏了这一点。
- 文档没写原因。最合理的解释是防止低温度下的循环和想不出结论（推断）。
- 限制：文档写的是云端 `qwen3.8-flash`，你跑的是开源的 Flash-Next，我没确认两者权重相同，只能当强参考。

**我现在的建议**

| 模式 | 建议温度 |
|---|---|
| 开思考（my agent stack 现在是 `xhigh`） | **0.6** |
| 关思考的短任务 | 可以更低，甚至 0（本地没测过） |

服务器默认值只能设一个，而 my agent stack 默认开思考，所以设 0.6。0.6 下的速度和接受率还没测过。**服务器默认值现在仍是 1.0，没有改动。**
